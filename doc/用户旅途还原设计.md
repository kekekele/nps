# 用户旅途还原设计

## 1. 目标与字段边界

以 `基础指标.手机号码` 为用户主键，生成时间升序的 `user_journey`。每条旅途固定输出字段为：`event_id`、`event_time`、`action`、`business`、`intent`、`source`、`raw_text`。

事件判断与规则仅使用下表字段；不得读取或使用其他 Sheet、其他列参与判断。

| Sheet | 允许字段 | `action` 归属 |
| --- | --- | --- |
| 业务订购 | 手机号码、操作时间、订购类型、资费名称 | 订购类型含“退订”为 `退订`，其他为 `办理` |
| 资费变更 | 手机号码、办理时间、宽带号码、变更标识 | `资费变更` |
| 限速与加包 | 手机号码、办理时间、业务类型 | 办理 |
| 狼号 | 手机号码、狼号接触时间、通话时长 | `狼号感染` |
| 投诉明细 | 手机号码、时间、投诉节点、明细 | `投诉` |
| 触点轨迹 | 手机号码、触点时间、触点小类、投诉类型、问题分类、语音转文本-客户、语音转文本-客服 | 可直接生成 `咨询` 或 `投诉` |

`basic_info` 和 `recent_metrics` 已表达用户其他特征，因此事件不设计 `context`。

## 2. 输出结构

```json
{
  "event_id": 682552975816343219,
  "event_time": "2026-07-06",
  "action": "投诉",
  "business": "套餐资费",
  "intent": "资费咨询",
  "source": "",
  "raw_text": ""
}
```

- `event_id`：由 `source_sheet + source_row_no + phone_id + event_time + source_business_key` 生成确定性的 63 位正整数哈希。检测到碰撞时加行号重算并记录质量告警。
- `event_time`：含时分秒时为 `%Y-%m-%d %H:%M:%S`；只含日期或 `YYYYMMDD` 时为 `%Y-%m-%d`，不补造 `00:00:00`。
- `action`：用户做了什么，承接原来粗粒度 `event_type` 的角色。当前固定取值为：`咨询`、`办理`、`资费变更`、`退订`、`投诉`、`狼号感染`。
- `business`：针对什么业务。通过预定义业务类目和正则规则，从不同 Sheet 的不同字段归类；未命中统一落到 `其他`。
- `intent`：为什么做，或用户的具体诉求/原因。通过预定义意图类目和正则规则，从不同 Sheet 的不同字段归类；未命中统一落到 `其他`。
- `source`：预留字段，当前实现固定输出空串，不回填数据来源。
- `raw_text`：预留字段，当前实现固定输出空串，不回填原始证据。

### 2.1 字段边界说明

当前版本刻意压平了原先的 `event_type + category` 设计：

- `action` 只回答“用户做了什么”。
- `business` 只回答“针对哪类业务”。
- `intent` 只回答“为什么做，或具体诉求是什么”。

例如一条由投诉文本识别出的事件可表示为：`action=投诉`、`business=套餐资费`、`intent=费用争议/退还`。这样“做了什么”和“为什么做”分开，避免 `action` 同时承载动作和原因。

当前实现中，`source` 和 `raw_text` 先保留字段位，方便后续做可追溯版本时再打开，不影响当前 JSON 结构稳定性。

## 3. 结构化事件固定逻辑

结构化字段不需要文本推断，按以下固定逻辑直接生成事件字段：

| 来源 | `action` | `business` | `intent` |
| --- | --- | --- | --- |
| 业务订购 | 订购类型含“退订”为 `退订`；其他为 `办理` | 从 `资费名称` 按业务正则归类；未命中为 `其他` | 分别固定为 `退订` 或 `订购` |
| 资费变更 | `资费变更` | 固定为 `套餐资费` | 由变更标识映射为 `平移/升档/降档`；未命中为 `其他` |
| 限速与加包 | `办理` | 从 `业务类型` 按业务正则归类；未命中为 `其他` | 由业务类型映射为 `限速/加包`；未命中为 `其他` |
| 狼号 | `狼号感染` | 固定为 `通信安全` | 固定为 `狼号接触` |
| 投诉明细 | `投诉` | 由投诉文本规则识别；未命中为 `其他` | 由投诉文本规则识别；未命中为 `其他` |

数值字段仅有狼号的通话时长；其缺失值为 `0`。事件输出不保留该原始值，通话时长仅可供后续独立分析使用，不能改变事件类别。

## 4. 触点轨迹事件生成

触点轨迹不生成独立的 `触点` 类，而会按可配置月份窗口直接生成两类 `action`：

- `咨询`：仅当 `触点小类` 包含“咨询”，且 `触点时间` 落在 `consultation_month_range` 内。
- `投诉`：仅当 `触点小类` 包含“投诉”，且 `触点时间` 落在 `complaint_month_range` 内。

除这两类外，其他触点轨迹行一律忽略，不再与主事件做 24 小时关联补充。

### 4.1 咨询事件

咨询事件来源仅限触点轨迹。其 `business/intent` 仅使用 `问题分类`、`语音转文本-客户`、`语音转文本-客服` 三列按规则提取；若未命中规则，则分别回落到 `其他`。

### 4.2 投诉事件

投诉事件有两个来源：

- `投诉明细` Sheet
- `触点轨迹` 中 `触点小类` 包含“投诉”的记录

两个来源统一受 `complaint_month_range` 约束，并按“手机号 + 时间 + action=投诉”去重；去重后优先保留非 `其他` 的 `business/intent`。

投诉的 `business/intent` 文本提取字段如下：

- 来自 `投诉明细`：`投诉节点`、`明细`
- 来自 `触点轨迹`：`投诉类型`、`问题分类`、`语音转文本-客户`、`语音转文本-客服`

原文不输出到 `user_journey`，只参与可配置规则匹配。`business` 和 `intent` 使用两套独立正则，允许同一条文本分别命中不同的业务归属和意图归属。当前实现不会把原始文本写回结果，只用于内部归类。

投诉相关规则按优先级执行：`intent` 侧仍按 `资费咨询` > `费用争议/退还` > `套餐变更/降档受阻` 匹配。`business` 侧使用独立规则表，按自身顺序匹配，不与 `intent` 共用正则。

初始规则组按事件类别配置，示例：

| 规则组 | 语音关键词/正则示例 | 规则输出 |
| --- | --- | --- |
| 资费咨询 | 资费咨询、套餐咨询、咨询资费 | business=套餐资费，intent=资费咨询 |
| 套餐变更或降档受阻 | 套餐变更、降档、无法办理、无法变更 | business=套餐资费，intent=套餐变更/降档受阻 |
| 费用争议或退还 | 费用争议、退费、退还、乱扣费 | business=套餐资费，intent=费用争议/退还 |
| 办理受阻 | 无法办理、办不了、强制绑定 | intent=办理受阻 |
| 退订受阻 | 无法退订、不能取消 | intent=退订受阻 |
| 资费争议 | 套餐贵、收费不合理、优惠到期 | business=套餐资费，intent=资费争议 |
| 流量使用争议 | 限速、流量不够、超套扣费 | business=流量服务，intent=流量使用争议 |
| 家宽问题 | 断网、掉线、无法上网、网速慢 | business=宽带服务，intent=网络问题 |

每条规则还配置否定正则，例如“未投诉”“问题已解决”“没有限速”。否定命中时该规则不生效。同一规则在多列同时命中时只生效一次。投诉事件优先匹配投诉专属规则，再回退到通用语音规则。

## 5. 配置、去重与验收

默认规则文件外置在 `nps_analysis/journey_config.yaml`，`nps_analysis/journey_config.py` 只负责把 YAML 解析为配置对象。配置核心思路是：

- 定义 `event_sources`，明确“从哪个 sheet、读取哪些字段、按什么行过滤、应用哪些规则、写到哪个输出字段”。
- 定义 `business_text_rules`，按 `action` 分组维护文本到 `business` 的映射。
- 定义 `intent_text_rules`，按 `action` 分组维护文本到 `intent` 的映射。
- 定义 `business_rules`，集中维护各类业务归类正则。

`event_sources` 的关键配置项包括：

- `sheet`：输入 sheet 名、表头行、数据起始行，以及手机号/时间列。
- `input_fields`：该来源允许读取的业务字段白名单。
- `row_filters`：例如 `触点小类` 包含“咨询”或 `订购类型` 不包含“退订”。
- `month_range_name`：绑定到 `consultation_month_range` 或 `complaint_month_range`。
- `action`：该来源生成的粗粒度动作。
- `intent_column + intent_rules`：把某个输入字段按规则映射到 `intent`。
- `output_bindings`：把输入字段原样或按变换写入 `business` 或 `intent`。
- `text_rule_fields`：需要拼接参与文本规则识别的字段。
- `business_key_fields` 与 `dedupe_fields`：分别控制 `event_id` 的业务键和去重键。

配置形态示意如下：

```yaml
default_business: 其他
default_intent: 其他

event_sources:
  - source_name: 业务订购
    action: 办理
    input_fields: [订购类型, 资费名称]
    row_filters:
      - column: 订购类型
        pattern: 退订
        match_type: contains
        negate: true
    default_intent: 订购
    output_bindings:
      - target: business
        column: 资费名称
        transform: business_category
    dedupe_fields: [$phone_id, $moment, $action, $business]

  - source_name: 触点轨迹
    action: 咨询
    input_fields: [触点小类, 问题分类, 语音转文本-客户, 语音转文本-客服]
    row_filters:
      - column: 触点小类
        pattern: 咨询
        match_type: contains
    month_range_name: consultation_month_range
    text_rule_fields: [问题分类, 语音转文本-客户, 语音转文本-客服]

business_text_rules:
  - action: 咨询
    rules:
      - rule_id: business.consult.broadband.v1
        pattern: 宽带|断网|掉线|无法上网|网速慢|家宽
        value: 宽带服务

intent_text_rules:
  - action: 咨询
    rules:
      - rule_id: consult.refund_dispute.v1
        pattern: 费用争议|退费|退还|退款|乱扣费|收费不合理|多收|资费争议
        value: 费用争议/退还
```

抽取引擎只做三件事：按 source 读取行、按 source 组装基础事件、分别按当前 `action` 对应的 `business_text_rules` 和 `intent_text_rules` 补齐 `business/intent`。这样字段来源、规则入口和输出绑定都集中在配置层，后续改 sheet、改字段名、加一个新来源，通常只需要改配置而不是改流程代码。

去重规则：业务订购按手机号、操作时间、`action`、业务归类；资费变更按手机号、办理时间、宽带号码、变更标识；投诉按手机号、时间、`action` 跨 `投诉明细/触点轨迹` 去重；其余事件保持来源内自然去重。咨询事件当前不跨来源合并，因为来源仅限触点轨迹。

排序键为时间、是否含时分秒、event_id，同日有具体时分秒的事件排在纯日期事件前。

实现新增 `nps_analysis/journey.py` 与 `tests/test_journey.py`：先标准化主事件，再解析触点直出咨询/投诉，去重排序后按手机号填入 `user_profile.build_user_profiles()`。

验收覆盖：六类 `action` 归属、业务/意图默认回落、订购退订分流、升降档映射、限速加包归入办理、咨询/投诉月份窗口、投诉跨来源去重、日期与秒级时间、语音规则与否定排除、字段白名单未被突破，以及全量 JSONL 可解析且每位用户旅途有序。
